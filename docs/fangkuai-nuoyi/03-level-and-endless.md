# 方块挪一挪 Web 版关卡系统与无限模式设计 v1.3

## 1. 文档定位
本文件用于定义：
- 主线关卡内容结构
- 关卡数据格式
- 无限模式的生成规则
- 可解校验方式
- 奖励与难度分层
- 在 Three.js 2.5D 渲染下需要遵守的数据与复杂度约束

本文件不是代码实现细节，而是策划与技术共享的数据与内容规范。

主线特殊方块分级、章节原型关卡草案、生成器硬约束/软约束/评分框架的详版说明，统一补充在 `docs/fangkuai-nuoyi/09-mainline-specials-and-generator-spec.md`。参考图提炼出的关卡结构、门系统和读盘标准，统一冻结在 `docs/fangkuai-nuoyi/10-level-design-standard-v3.md`。无限模式单档最终方案，统一冻结在 `docs/fangkuai-nuoyi/15-endless-mode-v1-brain-only.md`。

## 2. 主线关卡总体结构

### 2.1 总体规模
- 主线共 `12 章`
- 每章 `30 关`
- 总计 `360 关`

### 2.2 解锁规则
- 每章前 `20 关` 为主推进关
- 完成前 `20 关` 解锁下一章
- 后 `10 关` 为本章附加关，供愿意继续玩的玩家慢慢完成

### 2.3 单章内部节奏
- 第 `1` 章保持当前已试玩版本，不作为本轮统一调难对象。
- 第 `2~11` 章统一冻结为：`01~05 = 困难`、`06~20 = 专家`、`21~30 = 极难`。
- 第 `12` 章 `01~30` 全部为 `极难`。
- 只有新机制首次出现时，才允许把对应章节的 `01` 关做成“困难带内的教学关”；不再额外预留低压缓冲段。

### 2.4 棋盘尺寸与颜色基线
- 棋盘采用 `固定 6 列 + 8~12 行` 的手机优先规格。
- 主线常用盘面为 `6x8~6x10`。
- `6x11` 用于高压主线后段。
- `6x12` 仅用于极少数高难样本或无限模式高档位，且必须通过手机视口校验。
- 正式目标颜色池固定为 `6` 种：`red / blue / green / yellow / purple / orange`。
- 第 `1` 章固定使用 `4` 色，第 `2` 章固定使用 `5` 色，第 `3` 章起固定使用 `6` 色全部上。
- 主线关卡目标占格率统一控制在 `65%~80%`，章节内部再按 `困难 / 专家 / 极难` 做细分；第 `1` 章保持现状。

## 4. 主线关卡设计原则

### 4.1 每关必须有题眼
每一关都需要有一个玩家能看出来的中心问题，例如：
- 先把哪块挪出来
- 先开哪扇门
- 哪条狭道先打通
- 哪个颜色要先出去

### 4.2 不做隐藏规则难题
难度可以来自：
- 顺序
- 空间
- 组合

难度不应来自：
- 看不懂机关
- 看不清出口对应关系
- 机制第一次出现就混太多
- 因为 3D 角度导致观察困难

### 4.3 节奏关必须清晰，但不再刻意降档
- 第 `1` 章可保留少量低压力爽关，作为当前版本已经验证过的基线内容。
- 第 `2` 章起不再为了“呼吸”刻意做降档爽关。
- 所谓节奏关，只能是题眼更清晰、反馈更集中，而不是难度带下降。
- 即便是节奏关，也必须仍落在所属章节的 `困难 / 专家 / 极难` 目标带内。

### 4.4 附加关不阻断推进
附加关可以更复杂，但不应该卡住主流程解锁。

### 4.5 可视化优先于花哨布局
由于使用 Three.js 2.5D 渲染，关卡设计应优先保证：
- 出口在当前相机视角下清楚可见
- 棋盘边缘信息不被模型装饰遮挡
- 机关与地格拥有足够视觉对比
- 大方块不会因为高度和阴影让玩家误判占格

## 5. 关卡数据结构

### 5.1 存储格式建议
浏览器静态站点下，为兼容现有无构建流程，关卡建议使用 `ES Module 导出对象` 的方式存储，而不是依赖 JSON import。

推荐目录结构：
- `web_frontend/src/shift/data/campaign/chapter-01.js`
- `web_frontend/src/shift/data/campaign/chapter-02.js`
- `...`

每个文件导出本章数组。

### 5.2 LevelData 结构
```js

  chapter: 1,
  index: 1,
  title: '第一步',

    {

```

补充约束：
- `board.cols` 固定为 `6`。
- `board.rows` 在 `8~12` 间变化。
- `blocks` 当前版本默认全部为可清除目标块，不再区分“清除目标”和“占位阻挡”两种角色字段。

### 5.3 字段说明

#### 5.3.1 `style`
`style` 为颜色键，例如：
- `red`
- `blue`
- `green`
- `yellow`

该字段只负责定义方块与出口的颜色对应关系。
当前版本的 `blocks` 不再使用 `wood / stone / metal-soft` 这类中性材质键充当占位型块体。
中性材质只用于墙体、门和环境件。

#### 5.3.2 `moveAxis`
取值：
- `both`
- `horizontal`
- `vertical`

说明：
- `both` 不显示额外顶部图案。
- `horizontal / vertical` 必须显示箭头方向徽记。
- 被 `润滑油` 处理后，改显示“已润滑”状态徽记。

#### 5.3.3 `shapePreset`
用于指定该方块使用哪一类固定形状家族：
- `mono`
- `domino`
- `bar3`
- `square-2`
- `L-3`
- `L-4`
- `T-4`
- `cross-5`

配合字段：
- `shapeVariant`：记录方向或朝向
- `shapeCells`：规则层最终采用的真实占格

首发建议：
- 教学早期主要使用 `mono`、`domino`、`bar3`、`square-2`。
- `L` 从第 `2` 章起进入固定主线。
- `T` 从第 `3` 章起进入固定主线。
- `Z/S` 明确排除，不进入主线与无限模式 v1。
- 更详细的形状分级与组合限制见 `09-mainline-specials-and-generator-spec.md`。

#### 5.3.4 `shapeVariant`
用于描述形状当前采用的方向或朝向，例如：
- `default`
- `h / v`
- `ur / dr / dl / ul`
- `up / right / down / left`

要求：
- `shapeVariant` 必须能唯一映射到一组稳定的 `shapeCells`
- 同一关卡数据中，不允许仅凭 Mesh 旋转去推导变体

#### 5.3.5 `visualProfile`
用于指定 Three.js 表现层采用哪种视觉配置，例如：
- `rounded-toy`
- `wood-crate`
- `metal-switch`
- `finale-collage`

要求：
- `visualProfile` 只能影响外观，不影响规则
- 同一规则类型可共享多个视觉皮肤，但逻辑字段必须稳定

#### 5.3.6 `tiles`
用于放置地格类机制：
- `key_pad`
- `toggle_switch`
- `ice`
- `recolor`

#### 5.3.7 `gates`
用于描述门类结构：
- `lock_gate`
- `toggle_gate`
- `one_way_gate`

其中：
- `lock_gate` 通过 `keyPadIds` 或道具开启
- `toggle_gate` 通过 `switchIds` 翻转
- `one_way_gate` 通过 `allowDir` 判定方向

#### 5.3.8 `presentation`
用于关卡级 Three.js 展现配置，例如：
- 相机预设
- 场景光照组
- 特效等级
- 背景主题

约束：
- `presentation` 不得参与关卡可解性判断
- 即使没有该字段，关卡也应可正常运行

### 5.4 可选调试字段
固定关卡可额外携带以下字段，供调试与 QA 使用：
- `designerNote`
- `referenceSolution`
- `estimatedMoves`
- `tutorialHighlight`

说明：
- 因首版没有步数限制，这些字段不展示给玩家
- 但对难度校验、测试复现和后期维护很有价值

## 7. 无限模式定位

### 7.1 目标
无限模式用于满足两件事：
- 主线玩完后仍有内容
- 不想推进章节时，也能直接打开一直玩

但从现在开始，它外显只保留一个档位：`动脑`。

### 7.2 不是无上限爬塔，而是稳定高压带
无限模式是 `无限内容`，不是 `无限难度爬升`。

它也不再做 `轻松 / 普通 / 动脑` 三档分层，而是长期稳定维持在：
- **计划中的主线第 `6` 章后 `10` 关**
- 也就是 `第 6 章 brutal 带` 附近

允许少量上下波动，但不回落到明显低压的试玩盘。

### 7.3 无限模式也受渲染预算约束
无限模式不只要“可解”，还要“可稳定渲染”。

因此生成器还需满足：
- 活跃对象数受控
- 同屏特效数量受控
- 不启用对渲染最重的机制组合
- 不生成在当前相机视角下难以辨识的极端布局

## 8. 无限模式 v1 支持规则子集
为了优先保证可解、多样性和手机竖屏可读性，无限模式 v1 只使用以下元素：

支持：
- 所有可移动块都是 `可清除目标方块`
- `mono`、`domino`、`bar3`、`square-2`
- `L-3`、`L-4`、`T-4`、`cross-5`
- 方向限定块（单向块）
- `同色可多门` 的出口系统

明确不使用：
- 固定墙
- 独立占位阻挡块
- 锁门与钥匙格
- 单向门
- 简单开关门
- 变色格
- 冰面
- `Z/S` 异形块

这样做的原因：
- 无限模式 `v1` 明确对标计划中的第 `6` 章后 `10` 关
- 正式难度优先来自 `异形互锁 + 门前竞争 + 方向限定`
- 生成器更容易稳定控制 `颜色数 / 占地率 / 门预算 / 解法冗余 / 候选速度`
- 玩家在无限模式里也能维持与主线前六章一致的读盘语言
- 手机竖屏下更容易保持出口、颜色和局部战区的清晰度

## 9. 无限模式单档定义

### 9.1 动脑档（唯一外显档位）
- 对标：**计划中的主线第 `6` 章后 `10` 关**，不是当前仓库里的半成品第 `6` 章
- 内部 tier：`endless-peak`
- 棋盘：`6x9~6x10`
- 活跃颜色：`6`
- 目标占格率：`76%~80%`
- 目标块数：`18~24`
- 门预算：`8~10` 个门组、`11~14` 个门槽
- 机制：普通、异形、方向限定块（单向块）
- 解法要求：`solutionFamilyCount <= 2`，`openingActionCount = 1~2`
- 预估体验：持续保持第 `6` 章 brutal 带附近的高压读盘感
- 奖励：`80 金币 / 关`

### 9.2 连续奖励
- 连续完成 `5 关`：额外 `250 金币`
- 连续完成 `10 关`：额外 `600 金币`

## 10. 无限模式模板家族
无限模式不使用纯随机乱摆，而采用 `模板家族 + 参数扰动 + 求解校验`。

推荐首批模板家族：
- `dense-interlock`：高密度基础互锁型
- `dual-bottleneck`：双瓶颈串联型
- `gate-competition`：门前竞争型
- `shape-weave`：异形编织型
- `staged-release`：只靠几何结构实现的分阶段松动
- `axis-commit`：方向限定块迫使承诺某条轴线
- `hidden-first-clear`：首步不明显，但题眼清晰

每个模板家族至少提供：
- 适用难度档
- 棋盘尺寸候选
- 门组预算与门槽预算
- 方块数量范围
- 颜色数范围
- 可用机制列表
- 主工作区 / 主瓶颈 / 副瓶颈定义
- 反向扰动步数范围
- 推荐 `themeKey`
- 推荐 `cameraPreset`

## 11. 无限模式生成流程

### 11.1 生成总流程
1. 固定使用 `动脑` 档合同
2. 选择模板家族
3. 生成一个“可收尾”的基础骨架局
4. 按模板规则放置出口、目标块和关键瓶颈，并控制形状比例、门预算与颜色预算
5. 执行若干次 `逆向扰动` 把骨架打乱
6. 加入少量同类替换与位置扰动
7. 使用求解器验证可解性、门兼容、首步压力和解法冗余
8. 评估复杂度是否落在目标区间
9. 与最近若干局签名比对，避免过度重复
10. 检查移动端视口与渲染预算是否达标
11. 通过后写入本局 seed 并下发给前端

### 11.2 基础骨架局
基础骨架局是“从明显可清盘的布局出发”的起点，而不是直接随机摆满。

建议做法：
- 先保证每个目标块都存在一条清晰可达的兼容门路径
- 先定义 `主工作区 / 主瓶颈 / 门前区`，再填具体形状
- 若使用多格或异形块，需先验证其投影跨度与门宽关系
- 再逐步加入顺序依赖、颜色分流与门前竞争关系
- 最后再用逆向扰动把布局打散

### 11.3 逆向扰动
由于本游戏的移动是“沿轴向自由拖到合法位置”，因此一个合法位移在大多数情况下是可逆的。

生成器可以：
- 从一个容易清盘的状态出发
- 对若干块执行合法反向位移
- 记录这些反向步骤作为天然存在的正向解空间

优点：
- 更容易生成可解局
- 比从空白随机生成再硬筛选更稳定
- 更容易把门前竞争和阶段性松动保留下来

### 11.4 求解校验
必须使用求解器做最终校验，输出：
- `isSolvable`
- `bestMoveCountEstimate`
- `solutionFamilyCount`
- `openingActionCount`
- `doorGroupCount`
- `doorSlotCount`
- `mobileViewportFit`
- `stateHash`

说明：
- 即使玩家没有步数限制，求解器仍可用于衡量复杂度和过滤异常局
- `doorGroupCount / doorSlotCount` 用于控制多门分流是否失真

### 11.5 重复过滤
对生成出的候选局做签名：
- 棋盘尺寸
- 出口布局
- 目标块样式分布
- 主瓶颈位置
- 最短解长度带
- 模板家族 id

最近 `30` 局内，签名相似度过高则丢弃重生。

### 11.6 渲染预算检查
为配合 Three.js 渲染性能，候选关还应满足以下约束：
- 同屏可移动块总数不过高
- 门与机关总数受控
- 不触发多个高成本视觉元素同时出现
- 避免过多高亮元素集中在同一关

首版建议阈值：
- 活跃目标块总数尽量控制在 `24` 以内
- 活跃门组和机关总数尽量控制在 `10` 以内
- 单关使用的高亮材质种类尽量控制在 `6` 种以内

## 12. 无限模式 seed 与复现
- 每一局无限模式必须记录 `seed`
- 保存当前模板 id、难度档和 seed
- 这样便于：
  - 复现 bug
  - 开发调试
  - 退出后继续当前无限局

## 13. 无限模式的当前局保存
无限模式退出时保存：
- seed
- 当前盘面状态
- 当前轮次
- 当前连续完成数
- 当前已累计奖励
- 当前模板 id
- 当前 themeKey 和 cameraPreset

下次进入时提供两个选项：
- `继续本次无限模式`
- `重新开始新的一轮`

## 14. 关卡制作与维护建议

### 14.1 固定主线关卡
建议按章节拆文件维护，而不是 360 关放一个文件。

### 14.2 无限模板
建议单独按模板家族拆文件维护，例如：
- `templates-single-lane.js`
- `templates-center-chamber.js`
- `templates-lock-detour.js`

### 14.3 关卡标记
每个主线关卡在 `meta.tags` 中至少应包含：
- 难度标签
- 主题标签
- 机制标签
- 是否可用于教程

这样后续不做编辑器，也能通过数据结构稳定维护。

### 14.4 表现字段和规则字段分离
维护时必须遵守：
- 规则字段决定可解性
- 表现字段决定 Three.js 外观
- 不允许把规则条件藏进表现字段里

这样可以避免：
- 求解器与实际关卡规则不一致
- 渲染皮肤切换时破坏关卡逻辑
